# Probability change policy

Displayed estimates change only when a new release is promoted, and every change is
recorded, rounded honestly and explained. This page is the policy behind `delta.json`,
`changelog.md` and the "What changed" sections of the site.

## 1. When a displayed estimate may change

| Cause | Allowed? | Where recorded |
| --- | --- | --- |
| A new snapshot with new or corrected evidence, computed into a candidate and promoted | Yes | `delta.json` (`estimate_changes`, `index_changes`), `changelog.md`, manifest `changes` |
| A model version change (`internal/model` or `model_spec.json` parameters) | Yes, with the `model_version_changed` trigger | `delta.json` (`model_version_changed: true`), manifest `model_versions` |
| A rollback to an earlier release | Yes | audit event `release.rollback` with reason; the earlier release's own delta record applies |
| Editing a release directory | Never | `LoadDir` fails on a hash mismatch |
| Time passing | Never | The model reads no clock; `forecast_origin_date` is the release's `generated_at` date |
| A Scenario Lab session | Never | `user_scenario` results are not stored and are labelled as the user's assumptions |
| Ingestion or a public submission | Never | Review queue only |

## 2. Display rounding

Rounding is a function of the uncertainty label (build-spec rule 0.8,
[`../method/uncertainty.md`](../method/uncertainty.md)), stored in
`model_spec.rounding_rules` and applied by `internal/model/rounding.go` and
`@pdoom/model-core` (`roundForDisplay`, `formatInterval`):

| Uncertainty label | Step | Rule name in the estimate |
| --- | --- | --- |
| extreme | nearest 5 points | `nearest_5` |
| high | nearest 2 points | `nearest_2` |
| moderate | nearest 1 point | `nearest_1` |
| low | nearest 1 point | `nearest_1` |

Never decimals. A value that rounds below one point shows `<1%`; above ninety-nine, `>99%`;
intervals are written low–high with an en dash and collapse to one value when both ends round
the same. The official object uses `rounding_rule: "none"` because it publishes nothing.
Every estimate carries its `rounding_rule` and the UI prints it ("rounded to nearest 2 points")
next to the interval (`EstimateCard`). In `rel-2026-09-26-001` the external aggregates and the
research-mode estimates carry `uncertainty: high` and therefore `nearest_2`.

Because rounding depends on the label, a label change alone can change the displayed text
without any change in the underlying quantiles. Such a change is still a change: the delta
record compares `previous_p50` with `new_p50` (unrounded, four decimals) and separately shows
`previous_display` and `new_display`, so the reader can see that the text moved while the
value did not.

## 3. The delta record

`delta.json` (`DeltaRecordSchema`; produced by `internal/model/delta.go`) contains:

- `release_id`, `previous_release_id`, `snapshot_id`, `previous_snapshot_id`, `generated_at`;
- `estimate_changes[]`: `estimate_id`, `status`, `previous_p50`, `new_p50`, `change_points`
  (percentage points, four decimals, `null` when either side is missing), `previous_display`,
  `new_display`;
- `index_changes[]`: `index_id`, `previous`, `new`, `delta`;
- `heightened_review_triggers[]` ([`update-governance.md`](update-governance.md));
- `new_scenario_ids[]`, `new_forecast_source_ids[]`, `redefined_benchmark_ids[]`,
  `model_version_changed`;
- `notes[]` (for example "First release: no previous estimate to compare against." and
  "new estimate <id>").

For the first release every `previous_*` field is `null` and every `change_points` is `null`.

## 4. Change explanations

Three explanations travel with every release:

1. **Manifest `changes`**: generated by `internal/publishing.BuildManifest` from the delta: one
   line per estimate whose `change_points` is non-zero ("`<id>`: <old> → <new> (+x.x points)"),
   one per index that moved, or "No estimate or index moved relative to the previous release.";
   for a first release, "First release of this release line." and the snapshot counts.
2. **`changelog.md`**: the same lines plus the heightened-review triggers, the editorial level
   and any model warnings.
3. **Per-estimate `reason_for_change`** and `previous` pointer on each estimate object.

Reviewers add the human explanation in the changelog before approving: what evidence changed,
which compatibility group gained or lost a member, which parameter moved and why, with the
research report that justifies it. A release whose changelog cannot explain a movement is not
approved.

Causal attribution of a probability change to an individual driver is not available in this
model version; `drivers_explained.json` says so in its notes. The "What would change the
number?" panel uses index-point contributions and sensitivity runs instead
([`../method/sensitivity.md`](../method/sensitivity.md)).

## 5. No silent movement

- The meter (`MeterPanel`), `/changelog`, `/releases/[releaseId]` and `/text#changed` show the
  manifest `changes` and the triggers of the current release.
- `pdoomctl release diff <candidate>` prints the movement before anyone signs.
- Thresholds that force a second reviewer: any research-mode P_DOOM median moving by 2.0 points
  or more; any movement in an extinction (O6) estimate.
- The Evidence Pressure Index measures movement itself: it is fixed at 50 for the baseline
  release and moves with the change in capability, control and incident indexes against the
  baseline pointer propagated from release to release
  ([`../method/indexes.md`](../method/indexes.md)).
- Superseded releases stay readable with their own numbers, so a reader can always compare.

## 6. What the policy does not cover

- Scenario Lab outputs (`/lab`, `POST /v1/scenario-lab/evaluate`): user assumptions, labelled
  as such, compared on the page with the published research-mode run for the same horizon but
  never stored.
- Source values shown as source data (member forecasts, benchmark results): these are the
  records themselves and are shown with their original wording and precision on `/forecasts`,
  `/capabilities` and `/text`.

## Not yet implemented

- Automatic attribution of estimate movement to drivers (stated as unavailable in
  `drivers_explained.notes`).
- A second parameter set for the research-mode model as an "alternative prior" sensitivity run
  (planned in [`../method/sensitivity.md`](../method/sensitivity.md)).
